# PRS-001 disposable backup and PITR foundation

Status: **disposable validation tooling; not a production backup service**

This directory implements the first bounded proof required by issue `#122`. It uses an isolated Docker network, package-owned volumes and the exact image in `versions.env` to prove physical backup, encrypted recovery-set publication, prepare, isolated restore and point-in-time replay.

It does not connect to production, install a scheduler, configure a real object store, create a production Compose stack or authorize automatic restore/failover.

## Files

- `versions.env` — exact MariaDB version and immutable image digest.
- `take-full-backup.sh` — creates one physical full backup and records its binlog coordinate.
- `publish-recovery-set.sh` — rotates/copies binlogs, builds checksums and a redacted manifest, encrypts the payload and atomically publishes it to a filesystem storage boundary.
- `verify-recovery-set.sh` — verifies outer and inner checksums, decrypts the payload and validates the manifest.
- `restore-pitr.sh` — prepares/copies the physical backup, starts an isolated MariaDB container and replays binlogs to an approved UTC timestamp.
- `tests/integration/production-resilience/prs001-drill.sh` — disposable happy-path and failure-injection proof.

## Deliberate first-release boundaries

- Full physical backups plus archived binary logs are implemented.
- Incremental backups are deferred until the full-backup chain is stable.
- The filesystem artifact store in the drill models a separate failure domain but is not a production object-store adapter.
- The drill uses an ephemeral root password because all containers and data are disposable. A production adapter must use a least-privilege backup account and protected credential files.
- GnuPG symmetric encryption uses an ephemeral passphrase file generated by the drill. Production key custody, rotation and recovery remain deployment-owned.
- No RPO or RTO is claimed from CI timings.

## Local disposable drill

Requirements:

- Bash
- Docker Engine
- Python 3
- GnuPG
- GNU `sha256sum`, `tar`, `find`, `sort` and `xargs`

Run from the repository root:

```sh
tests/integration/production-resilience/prs001-drill.sh
```

The script creates unique containers, a network, volumes and temporary host directories. Its cleanup trap removes only those package-owned resources. Set `PRS001_KEEP_WORKDIR=1` to retain disposable evidence after a failure; never point the drill at a production path.

## Recovery-set format

Each published directory contains:

```text
manifest.json
payload.tar.gpg
SHA256SUMS
```

The encrypted payload contains:

```text
payload.tar
FILES.sha256
```

`payload.tar` contains the physical backup and archived binlog files. `FILES.sha256` protects every file inside that payload. `SHA256SUMS` protects the encrypted payload and redacted manifest after publication.

Publication uses a temporary directory under the destination and renames it only after checksum verification. An existing recovery-set identifier is never replaced, and failed publication does not delete a previous known-good set.

## Production gate

A later production adapter must still provide and validate:

- a real off-host immutable/versioned object store;
- production credential and key custody;
- scheduler ownership and concurrency control;
- retention and deletion policy;
- metrics and alert delivery;
- capacity and duration measurements;
- isolated restore drills using production-shaped data;
- an operator-approved cutover procedure.

`docker/docker-compose.yml` remains the local quickstart and is intentionally not used or modified by this package.
